# Исправление обработки ошибок 429 (Rate Limit)

## Проблема
GigaChat API возвращал ошибки 429 (Too Many Requests), и существующий retry механизм:
1. Не работал корректно для streaming запросов
2. Не использовал jitter, что приводило к "thundering herd" эффекту
3. Не имел адаптивного rate limiting
4. Пытался делать retry после начала стриминга (невозможно)

## Решение

### 1. Улучшенный Retry с Jitter
- Добавлен random jitter к задержкам (0.5-1.5x от базовой задержки)
- Увеличено количество попыток: 1s → 2s → 4s → 8s
- Предотвращает одновременные запросы от всех клиентов

### 2. Адаптивный Rate Limiter (`app/utils/rate_limiter.py`)
- **AdaptiveRateLimiter** класс для управления частотой запросов
- Автоматически увеличивает задержку при 429 ошибках
- Постепенно уменьшает задержку при успешных запросах
- Circuit breaker: блокирует запросы при 5+ последовательных 429 за минуту

### 3. Правильная обработка Streaming
- Retry работает **только до начала стриминга**
- После первого `yield` retry невозможен - сразу выбрасывается ошибка
- Флаг `stream_started` отслеживает состояние

### 4. Использование Retry-After заголовка
- Если API возвращает `Retry-After`, используется это значение
- Максимальная задержка ограничена 30 секундами

## Измененные файлы

### `app/providers/models/gigachat_provider.py`

- Исправлен метод `stream()` - retry только до начала стрима

### `app/services/embedding_service.py`
- Обновлена функция `_with_retry()` с jitter

- Класс `AdaptiveRateLimiter` для управления частотой запросов

- Exponential backoff с адаптацией

## Как это работает

### Обычный запрос (generate)
```
1. Проверка circuit breaker
2. Ожидание согласно rate limiter
3. Выполнение запроса
4. Если 429:
   - Уведомление rate limiter
   - Ожидание с jitter
   - Повторная попытка (до 5 раз)
5. При успехе: уведомление rate limiter → уменьшение задержки
```

### Streaming запрос
```
1. Проверка circuit breaker
2. Ожидание согласно rate limiter
3. Начало запроса
4. Если 429 ДО первого chunk:
   - Retry с jitter
5. Если 429 ПОСЛЕ первого chunk:
   - Немедленная ошибка (retry невозможен)
6. При успехе: уведомление rate limiter
```

## Преимущества

1. **Меньше нагрузки на API**: адаптивные задержки между запросами
2. **Нет thundering herd**: jitter распределяет запросы во времени
3. **Автоматическое восстановление**: постепенное уменьшение задержек
4. **Circuit breaker**: защита от лавинообразных ошибок
5. **Правильная обработка streaming**: нет попыток retry после начала стрима

## Мониторинг

Логи теперь показывают:
- Текущую попытку и задержку с jitter
- Состояние rate limiter
- Активацию circuit breaker
- Использование Retry-After заголовка

Пример:
```
2026-04-15 11:32:28 | WARNING | 429 от GigaChat stream, попытка 2/5, жду 1.73с
2026-04-15 11:32:30 | WARNING | Circuit breaker активирован - слишком много 429 ошибок
2026-04-15 11:32:35 | INFO    | GigaChat stream completed: 1234 chars, 5678.90ms
```

3. Настроить алерты на активацию circuit breaker
4. Рассмотреть использование очереди запросов для высоконагруженных систем
